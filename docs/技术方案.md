# GmailPing V1 技术方案

设计稿 · 2026-11-19 · 对应[产品需求](产品需求.md)

## 应用结构

一个 Swift 原生应用进程持有一个 NSStatusItem。所有邮箱共享网络会话、系统通知中心和调度器。每个邮箱独立持有凭据、同步位置、最后成功快照以及退避状态。默认账号只是浏览器打开目标，轮询器直接从账号列表取任务。

| 模块 | 责任与边界 |
| --- | --- |
| Application / Settings | AppKit 管理生命周期，LSUIElement 隐藏 Dock 图标，SwiftUI 承载引导和设置。SMAppService.mainApp 管理登录项。首次登记后以系统状态为准，尊重用户在系统设置的变更。[Apple Service Management](https://developer.apple.com/documentation/servicemanagement/smappservice) |
| MenuBar / BrowserLauncher | 在主线程更新按钮的图片、标题、辅助功能文本。监听左／右键抬起，按事件显示 NSMenu 或打开默认邮箱。按账号构造 URL，由 NSWorkspace 交给默认浏览器。 |
| Accounts / OAuth | 管理添加、重新授权、移除及默认账号。按 Google 身份刷新凭据。浏览器授权事务与后台 API 请求独立。 |
| Gmail / Sync | URLSession 调用 Gmail API。每账号串行处理历史、筛选候选、读取计数并提交。将已提交的账号快照交给界面汇总。 |
| Scheduler | Swift Concurrency 可取消任务，结合 NWPathMonitor 和 NSWorkspace 睡眠／唤醒事件调度。 |
| Storage / Notifications | Keychain 保存令牌，本地文件提交账号状态，UserDefaults 保存偏好。UNUserNotificationCenter 按账号投递、检查权限和处理点击。 |

## Google 授权与账号身份

1. 在 Google Cloud 项目启用 Gmail API，建立 Desktop app OAuth 客户端，按实际受众配置同意屏幕及测试用户。邮箱查询只请求 `https://www.googleapis.com/auth/gmail.metadata`。另请求 `openid` 获取稳定身份。显示邮箱由 Gmail profile 提供，无需额外请求通讯录、头像或邮件内容权限。[Gmail 权限](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Gmail Profile](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile)
2. 在系统浏览器发起授权码流程。每次生成独立 state、nonce 和 PKCE S256 verifier/challenge，通过短时监听的随机本机回环端口接收回调，仅接受本次事务匹配的回调。取消或超时关闭监听并作废事务。添加时允许选择 Google 账号，重新授权时带上目标账号提示。[桌面 OAuth 流程](https://developers.google.com/identity/protocols/oauth2/native-app)
3. 交换授权码后检查实际授予的 scope，校验 ID token 签名、发行方、受众、有效期与 nonce，使用验证后的 Google `sub` 唯一识别账号。以同批凭据读 `users/me/profile` 取得当前邮箱地址。邮箱改名仅更新显示和网页目标。若重新授权返回不同 `sub`，丢弃此次结果并提示重新选择。[Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
4. 请求离线访问。对已有账号，刷新响应未提供新 refresh token 时保留原有值。新账号缺少可用 refresh token 时引导再次同意。在可持续刷新前不显示为连接成功。每账号同时最多一个刷新请求。失败按下表处理。

## 持久化与账号生命周期

| 存储 | 内容与写入时机 |
| --- | --- |
| Keychain | 为每个本地账号实例生成 UUID，作为 Keychain account。service 固定为应用标识。access token、过期时间、refresh token 同项更新，使用本机非同步条目。 |
| Application Support 的账号目录 | 版本号、账号实例 UUID、Google sub、邮箱地址、添加顺序、默认账号及待清理标记。单个存储 actor 串行原子替换目录清单。 |
| 每账号同步文件 | historyId 字符串、最近成功时间、未读数、有限的近期已处理邮件 ID，以及待投递批次的状态。将同一次检查的结果编码为一个快照，用临时文件原子替换。 |
| UserDefaults | 全局检查周期、数字、声音、通知和启动摘要偏好。登录项生效状态实时从系统查询。 |

添加时先完成身份验证、写凭据，再发布账号记录。启动时清理仅属于本应用且无账号记录的孤立凭据。遇钥匙串暂不可读或目录读取失败时暂缓清理。相同 sub 复用既有记录。移除时先持久化待清理标记，使该实例立即退出汇总与调度，再取消任务，清理令牌、文件及系统通知。重启继续未完成的清理。移除后再次添加产生新实例，旧通知及迟到的网络回调无法写入新实例。退出本地账号不改变浏览器会话。

## 单账号增量检查

以下操作都在指定账号的授权上下文中调用 `users/me`。每个账号的检查按顺序执行，部分成功只保留为内存中的候选结果。

1. **建基线。** 首次连接、同步文件缺失或游标过期时，先用 `users.getProfile` 取当前 historyId，再用 `users.labels.get(INBOX)` 取 `messagesUnread`。两者成功后一起落盘。基线采样后的新到邮件会在后续 history 中出现，即使其未读数已经计入首次快照。[Profile](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile) · [Labels](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/get)
2. **收集新 ID。** 从已提交的 `startHistoryId` 调 `users.history.list(historyTypes=messageAdded)`，依次使用 nextPageToken，收集各页 `messagesAdded[].message.id`。页内和跨页去重。忽略通用 messages 数组和纯标签变化。historyId 按 API 返回的字符串原样保存，直到末页才获得本轮可提交的位置。[History](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)
3. **确认当前收件箱范围。** History 内嵌消息可能只有 ID。只对新的候选 ID 请求 `users.messages.get(format=minimal, fields=id,labelIds)`，按当前标签包含 INBOX 且无 SPAM、TRASH 筛选。无需 UNREAD。候选消息已删除返回 404 时跳过该条。此处“新”定义为 Gmail 新增了消息资源，导入收件箱的邮件也可能满足条件。V1 不从主题、日期或发件人推断送达来源。[Messages](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get)
4. **更新计数并提交。** 每轮都单独读取 INBOX.messagesUnread，包括 history 无变化时。把末页 historyId、未读数、成功时间、去重结果及本轮通知意图一起原子提交。网络、分页或保存失败均从原游标重试。history.list 对过期位置返回 404 时只重建该账号基线。其他接口的 404 不能触发同一恢复逻辑。[增量同步指引](https://developers.google.com/workspace/gmail/api/guides/sync)
5. **投递。** 只为可通知的候选生成一条账号级批次，标识由账号实例和本次游标区间确定。近期 ID 按账号有界保存，正确的分页边界和单账号串行提交保障同一历史区间不会被分割提交。通知设置关闭或系统拒绝时照常完成同步并消费该批次，恢复权限后不补发。

应用状态与 macOS 通知中心无法共同提交事务。采用“尽量送达，崩溃时优先避免重复打扰”的取舍。持久化待发批次后，先将其标记为投递中，再以固定标识调用系统。启动时恢复尚未尝试的批次。对投递中的批次比对系统 pending/delivered 记录，若结果不明则结束该批次。这样在标记完成与系统受理之间突然退出可能少一条通知。邮箱计数和下次检测位置仍保持一致。系统明确拒绝请求时记录可读状态，不循环弹窗。

## 调度、错误与网络开销

| 事件或结果 | 行为 |
| --- | --- |
| 启动、到期、手动、唤醒或重新联网 | 共享触发入口。手动模式仅接受用户检查与授权后的必要同步。每账号至多一个在途检查，全局初始并发上限为 2，不同账号错开轮询。系统唤醒与网络恢复同时到达时合并。 |
| 无网络、超时、Google 5xx | 保留快照和旧游标。自动模式按账号指数退避并加随机抖动，建议从 30 秒至 15 分钟。离线时挂起网络任务，网络恢复后重新排队。 |
| 429、403 rateLimitExceeded / userRateLimitExceeded | 遵循 Retry-After，以较晚的可重试时间为准。用户级限流只推迟对应账号。明确的项目级配额耗尽时协调全部请求。手动检查也尊重服务端等待时间。 |
| 401、invalid_grant、权限被管理员限制 | 401 先刷新并重放一次。凭据撤销或缺失授权时，仅将该账号标为「需要重新授权」并停止自动请求。策略阻止时提示相应原因。 |
| 睡眠／退出、设置变更 | 睡眠暂停，退出取消任务。变更周期重新安排。取消后检查账号实例及任务有效性再落盘。手动模式下失败可再次点击检查。 |
| 通知被阻止／钥匙串锁定 | 设置中展示系统权限状态并提供对应操作。通知不可用仍提交计数。钥匙串锁定标为暂不可用，解锁后重试，保留凭据。 |

稳定无变化时，每账号每轮通常一次 history 和一次标签查询。按 60 秒周期，两个账号约 4 次 Gmail 查询／分钟，另计分页、候选标签查询与偶发刷新。全局并发限制也覆盖候选查询，避免一个大邮箱独占所有请求。空闲时挂起任务，避免用高频定时器扫描。

## 通知、网页与图标实现

- 通知负载使用本地账号实例 UUID，副标题取显示邮箱。分组及请求标识含账号实例。点击时重新解析实例。若账号已移除，打开账号管理。首个账号由用户连接后说明通知用途并调用系统授权。登录项后台启动不主动弹出授权引导。
- 浏览器路由输入为目标账号当前邮箱。候选实现为用 URLComponents 对邮箱编码后生成 Gmail 收件箱地址（如 `https://mail.google.com/mail/?authuser=work%40example.com#inbox`）。这是待实测的网页行为，Gmail REST API 不提供浏览器会话保证。不得保存 `/u/0` 等登录序号。若验证发现目标被忽略，改走 Google 账号选择入口并显示目标地址。以双账号实机测试作为路由验收依据。
- 将应用图标、菜单栏图像、服务入口素材分开配置。官方原图在获准的用途以原色绘制（NSImage.isTemplate 为 false），提供高分辨率素材。独立菜单栏符号使用模板渲染。NSStatusBarButton 的独立 title 承载数量，避免缩放或在品牌图形上烘焙数字。公开包的选择见[产品需求](产品需求.md)。
- 启动摘要只对系统登录项启动生效，需从 macOS 启动事件识别并真机验证。普通手动重开应用按增量规则处理。摘要沿用同一账号投递流程，在该次系统登录启动中只尝试一次。

## 构建与分发

使用 Xcode，部署目标 macOS 13，优先 arm64，同时构建并验证 x86_64。个人验证使用自有 Cloud 项目及测试邮箱。公开分发使用 Developer ID 签名、公证并验证下载包。同时核对项目名称、图标用途与 gmail.metadata 的受限权限审核要求，按真实部署方式评估。OAuth 测试受众、令牌有效期和可发布状态以实际 Cloud 项目为准。日志仅记录操作类型、错误类别、耗时与汇总数量。[Google 受限权限](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
